# 문맥이 애매한 질문 처리 로드맵

> 현재 파이프라인(벡터DB + 위키)은 **질문 어휘가 공시 원문과 일치할 때**만 안정적으로 동작한다.
> 이 문서는 어휘가 다르거나(동의어), 개념으로 묻거나(인건비 → 급여총액), 서술·판단을 요구하는 질문을
> 처리하도록 확장하는 방법을 단계별로 정리한다.

---

## 0. 현재 한계 (실측)

삼성전자 8건(15,904 청크) 인덱스에서 검색만 수행한 결과.

| 유형 | 질문 | 결과 | 원인 |
|---|---|---|---|
| 정확 어휘 | 2023년 사업보고서 영업이익 | ✅ 요약재무·경영진단 표 KV | 질문 단어 = 표 라벨 |
| ① 동의어 | 2023년 사업보고서 **영업손익** 규모 | ❌ | 해싱 임베딩 코사인 `영업이익↔영업손익` = **0.25** |
| ② 개념→항목 | 2023년 사업보고서 **인건비 부담**은? | ❌ | `인건비↔연간급여총액` = **0.00** (공유 글자 없음) |
| ③ 서술·판단 | 반도체 **업황 악화가 실적에 미친 영향** | ❌ | 경영진단 서술 문단을 못 찾고 숫자 토큰(`2023`) 많은 무관한 표로 빠짐 |
| ③ 서술·판단 | **현금 창출력**이 좋아졌어? | ❌ | `현금창출력↔영업활동현금흐름` = 0.16 |

원인 요약:
- `store.py`의 기본 `HashingEmbedder`는 char n-gram 해싱이라 **의미 벡터가 아니다** (BM25의 다른 표현). 하이브리드라 해도 실질은 어휘 매칭 2개.
- 데모 7문항이 맞은 이유는 메타 필터(`report_type/period`) + 섹션 제목 토큰 부스트 + LLM 독해였고, 검색 자체의 시맨틱은 없었다.
- 청크의 92%가 표(그중 절반이 재무제표 주석)라 텍스트 질문이 표 수천 개와 경쟁한다.

## 1. 목표 아키텍처

"질문 → 벡터 1개 → top-k" 한 방에서 **"질문 이해 → 위치 결정 → 세부 검색 → 재정렬"** 단계형으로.

```
질문
 ├─ [2a] 용어 사전 확장 ────────────────┐
 ├─ [2b] HyDE 가상 답변 생성 (LLM 1회) ─┤
 └─ [2c] 섹션 라우팅 (위키 목차, LLM 1회)┤
                                        ▼
        [4] 수치 조합형? ─yes─▶ facts SQLite (text-to-SQL) ─▶ 표 답변
              │ no
              ▼
   [1] 섹션 필터 + 하이브리드 (bge-m3 dense + Kiwi BM25) → 후보 30
              ▼
   [3c] 크로스인코더 리랭크 → 8
              ▼
   [3b] parent_id 로 위키 섹션 본문/표 확장 (small-to-big)
              ▼
   LLM 답변 + 출처 [n]
```

## 2. 단계별 방법

### 1단계. 진짜 임베딩으로 교체 — ①·② 절반 해결, **필수**

- `store.py`에 `Embedder` 클래스 추가 (`embed(texts)->ndarray`, `name`, `dim` 만 구현).
- 후보
  | 모델 | 차원 | 특징 | CPU 속도(15,904청크) | GPU(4090) |
  |---|---|---|---|---|
  | `intfloat/multilingual-e5-small` | 384 | 가볍고 빠름 | ~8분 | 수 초 |
  | `BAAI/bge-m3` | 1024 | 한국어 최상급, 하이브리드 지원 | ~25분 | ~10초 |
  | Gemini `text-embedding-004` | 768 | 무료 API 티어 | API 속도 | - |
- 임베더가 바뀌면 `data/vectordb` 를 삭제 후 재 `ingest` (info.json 의 embedder 명이 다르면 자동 무시).
- 기대: `영업이익↔영업손익` 0.25 → 0.8 수준. 이때부터 BM25(정확 숫자·기수·고유명사)와 dense(의미)가 **서로 다른 역할**을 맡아 RRF 융합이 실제 의미를 가진다.

```python
# store.py 예시
class STEmbedder:
    def __init__(self, model="intfloat/multilingual-e5-small"):
        from sentence_transformers import SentenceTransformer
        self.m = SentenceTransformer(model); self.name = model; self.dim = self.m.get_sentence_embedding_dimension()
    def embed(self, texts):
        return self.m.encode(texts, normalize_embeddings=True, batch_size=64)
```

### 2단계. 질문 이해 층 — ② 해결, 비용 거의 0

검색 전에 질문을 **문서의 언어**로 바꾼다. 셋을 겹쳐 쓴다.

**2a. 공시 용어 사전 (규칙, 무료)**
공시 계정과목은 유한하다. 100줄이면 대부분 덮는다. `rag.py retrieve()` 직전에 질문 토큰을 확장해 BM25 쿼리에 붙인다.

```python
SYNONYMS = {
  "인건비":     ["급여", "연간급여총액", "종업원급여", "1인평균급여액"],
  "현금창출력": ["영업활동현금흐름", "영업활동으로 인한 현금흐름", "EBITDA"],
  "영업손익":   ["영업이익", "영업손실"],
  "빚":         ["부채총계", "차입금", "사채"],
  "배당":       ["현금배당금", "주당 배당금", "배당성향", "배당총액"],
  "직원":       ["직원 수", "임직원", "근로자"],
  "R&D":        ["연구개발비", "연구개발활동"],
  "대주주":     ["최대주주", "5% 이상 주주", "특수관계인"],
}
```

**2b. HyDE — LLM 질문 재작성 (Groq 1회, ~300토큰)**
"이 질문에 답이 될 사업보고서 문장을 2줄 써봐" → 가상 답변으로 검색한다. 질문이 아니라 **답의 형태**로 검색하므로 문서와 어휘가 맞는다. ③ 서술형에 특히 효과적.

```
Q: 인건비 부담은 어느 정도야?
가상답변: 당사의 연간급여총액은 14조 4,782억원이며 1인평균급여액은 1억 2천만원입니다. 직원 수는 124,804명입니다.
→ 이 문장을 임베딩·BM25 쿼리로 사용
```

**2c. 섹션 라우팅 (위키 목차 활용, Groq 1회)**
DART 목차는 53개로 고정이라 프롬프트가 짧다(~800토큰). LLM이 답이 있을 섹션을 최대 3개 고르면, 이후 검색을 `where={"section_path": ...}` 로 그 안에서만 수행 → **주석 표 7,970개와 경쟁하지 않는다.** 어휘가 하나도 겹치지 않아도 라우팅된다. 현재의 "섹션 제목 토큰 부스트"를 LLM 판단으로 대체하는 것.

```
[목차]  I. 회사의 개요 > 1~5 / II. 사업의 내용 > 1,2,3,4,5,6,7 / III. 재무 > 1~8 /
        IV. 이사의 경영진단 및 분석의견 / ... / VIII. 임원 및 직원 > 1,2 / ...
[질문]  인건비 부담은 어느 정도야?
[출력]  ["VIII > 1. 임원 및 직원 등의 현황", "III > 2. 연결재무제표", "IV. 이사의 경영진단 및 분석의견"]
```

### 3단계. 계층 검색 + 리랭커 — ③ 해결

**3a. 섹션 요약 인덱스 (상위층)**
위키 424개 섹션 페이지마다 LLM 요약 ~200자를 생성해 별도 임베딩(Bogosa의 RAPTOR 층에 해당). 질문은 먼저 이 상위층에서 섹션을 고르고 그 안에서 청크를 찾는다. 규모가 커져도 상위층은 "회사×보고서×섹션" 수만 건이라 브루트포스로도 빠르다. 2c와 상호보완.

**3b. 부모 확장(small-to-big) 강화**
서술형은 청크 1개로 답이 안 된다. 걸린 청크의 `parent_id`로 **위키 섹션 페이지 전체**를 컨텍스트에 넣는다. 현재는 표 KV만 동반하므로 `rag.py`에서 텍스트 섹션 본문도 포함하도록 수정. 경영진단(12,000자)처럼 긴 섹션은 3a 요약본 또는 상한 절단.

**3c. 크로스인코더 리랭커**
후보 30개 → `BAAI/bge-reranker-v2-m3` 가 질문과 청크를 **한 쌍씩 같이 읽고** 점수 → 상위 8개. 임베딩보다 문맥 판단이 정확해 애매한 질문에 가장 직접적으로 듣는다.
- CPU 질문당 2~3초, GPU 0.1초.
- Groq LLM listwise 리랭킹(Bogosa 방식)으로 대체 가능하나 무료 티어 8k TPM 부담이 크다.

### 4단계. 수치 질문은 구조화 질의로 — 선택, 강력

"3년간 영업이익 추이", "DS부문 매출 비중"처럼 **여러 칸을 조합**하는 질문은 벡터 검색이 근본적으로 약하다. KV 선형화가 이미 `(회사, 보고서, 섹션, 행라벨, 열헤더, 값, 단위)` 튜플이므로 그대로 SQLite `facts` 테이블에 넣는다.

```sql
SELECT period, col_header, value_num, unit FROM facts
WHERE corp='삼성전자' AND row_label LIKE '%영업이익%' AND section LIKE '%요약재무%'
ORDER BY period;
```
- LLM이 SQL 생성(text-to-SQL) → 결과를 표로 답변.
- 선행 작업: 숫자 정규화(`△230,152` → `-230152`), 기수↔연도 매핑(`제55기` → 2023), 연결/별도 플래그.
- 벡터 검색 옆의 **두 번째 경로**. 질문 라우터가 "수치 조합형"이면 이쪽으로.

### 5단계. 평가셋 — 없으면 위 전부가 감이 된다

30~50문항: 원문 어휘형 10 / 동의어형 10 / 개념형 10 / 서술형 10, 각각 정답 섹션·수치 기재.
각 단계 적용 시마다 **recall@5 / precision@5** 를 기록한다. (Bogosa 의 RAGAS score 파일이 이 역할이었고, 그들 실험에서 청킹 방식보다 메타 필터가 recall .79 → 1.0 을 만든 것이 확인됐다.)

## 3. 적용 순서 (효과 대비 비용)

| 순서 | 작업 | 필요 자원 | 기대 효과 | 변경 파일 |
|---|---|---|---|---|
| 1 | 용어 사전 + 섹션 라우팅(Groq) | 없음 | ② 상당 부분, ③ 라우팅 | `rag.py` |
| 2 | e5-small 로컬 임베딩 | CPU 8분 | ① 해결 | `store.py` |
| 3 | 평가셋 30문항 + recall 측정 스크립트 | 반나절 | 이후 판단 근거 | `eval/` 신규 |
| 4 | HyDE + 부모 섹션 본문 확장 | Groq 호출 +1 | ③ | `rag.py` |
| 5 | (GPU 확보 후) bge-m3 + bge-reranker | 4090 | 전체 품질 한 단계 | `store.py`, `rag.py` |
| 6 | facts SQLite + text-to-SQL | 파서 보강 | 시계열·비교 질문 | `chunker.py`, `facts.py` 신규 |

1~2는 코드 100줄 이내.

## 4. 규모 확장 시 함께 바꿀 것 (참고)

KOSPI 200 × 3년(≈2,400건, ≈170만 청크) 기준 현재 구조는 RAM 13GB+ 필요 → 노트북 불가.

- `chunks.jsonl` → SQLite(메타+raw), 벡터 → Chroma/LanceDB/Qdrant-local (HNSW, 디스크 mmap, int8)
- `table` 마크다운은 임베딩하지 않고 메타로만 보관, **`table_kv` 만 임베딩** → 벡터 40% 감소
- 재무제표 주석 표는 "주석 번호 + 표 제목" 단위로 통합, 질문이 주석을 명시할 때만 세부 검색
- 3a 상위층(섹션 요약 12만 건) → 하위 청크 2단계 검색
- `[기재정정]` 공시는 최신본만 유지
- 텍스트 인덱스 / 표 인덱스 / 원문 저장소 3층 분리 (현재는 `kind` 메타로 구분한 단일 인덱스)

결과: 디스크 4~5GB, RAM 1GB 이내. 유일한 병목은 임베딩 계산 → GPU 또는 API.
