# 코드 가이드

DART 공시(사업·반기·분기보고서)를 미리 가공해 두고, 사용자 질문에 공시 원문을 근거로 답하는 백엔드입니다.
공시 1건을 기업분석 보고서로 정리하는 기능도 있습니다.

- 설치와 실행 방법: [README](../README.md)
- 이 문서: 프로그램이 어떻게 동작하고, 코드가 어디에 있으며, 왜 그렇게 만들었는지

---

## 용어

| 용어 | 뜻 |
|---|---|
| 공시 | DART에 올라온 정기보고서 1건 (예: SK하이닉스 반기보고서 2026.06) |
| 청크 | 검색을 위해 공시를 잘게 나눈 조각 (문단 또는 표 일부) |
| 위키 | 공시를 `기업 → 보고서 → 섹션` 순서의 페이지로 정리해 둔 것. 섹션 이름으로 바로 찾아 읽을 수 있습니다 |
| 근거 | 답변의 바탕이 된 공시 원문 부분 |
| 라우터 | 질문을 보고 어떤 방법(경로)으로 답할지 정하는 단계 |
| 경로 | 근거를 모으는 방법. 아래 네 가지 중 하나입니다 |
| └ 위키 경로 | 해당 섹션 페이지를 바로 읽습니다. 검색을 하지 않아 가장 빠릅니다 |
| └ 하이브리드 경로 | 의미 검색과 단어 검색(BM25)을 함께 씁니다 |
| └ 벡터 경로 | 의미 검색만 씁니다. 원인이나 전망을 묻는 질문에 씁니다 |
| └ 에이전트 경로 | LLM이 도구를 골라 가며 여러 단계로 조사합니다. 복잡한 질문용이고 가장 느립니다 |
| Luna | 답변과 보고서를 쓰는 LLM (GPT-6 Luna) |
| Gemini | 라우터 판단을 돕는 가벼운 LLM (gemini-3.5-flash-lite) |
| 저장본 | 미리 만들어 둔 보고서 파일. 요청하면 바로 보여 줍니다 |

## 1. 전체 구조

프로그램은 세 부분으로 나뉩니다.

```
① 데이터 준비 (미리 한 번 실행)
   공시 다운로드 → 구조 분석 → 청크 나누기 → 임베딩 → 검색 인덱스 → 위키 → 보고서
                                                         결과는 모두 data/ 폴더에 저장

② 질문 답변 (질문마다 실행)
   질문 → 라우터 → 경로 선택 → 근거 수집 → Luna 답변 → 숫자 검증 → 응답

③ 보고서 (웹의 '보고서' 탭)
   저장본이 있으면 바로 보여 주고, 없으면 섹션별로 작성한 뒤 저장
```

## 2. 질문 하나가 처리되는 과정

기본 모드(auto) 기준입니다.

| 순서 | 하는 일 | 코드 위치 |
|---|---|---|
| 1 | 질문을 받습니다 | `api.py` → `service.py` |
| 2 | **규칙 라우터**가 질문 속 단어로 회사, 기간, 섹션을 찾습니다. 모두 확실하면 위키 경로로 정하고 3번으로 갑니다 | `routing/router.py` |
| 2-1 | 확실하지 않으면(동의어, 원인 질문 등) **Gemini**에게 경로를 묻습니다. Gemini가 실패하면 규칙 라우터의 판단을 씁니다 | `routing/router.py` |
| 3 | 정한 경로로 근거를 모읍니다 | `routing/auto.py` |
| 4 | **Luna**가 근거만 보고 답변을 씁니다 (결론, 주요 내용, 해석, 근거) | `routing/auto.py` |
| 5 | 답변에 인용된 숫자가 실제 원문에 있는지 확인합니다 | `agent/loop.py` |
| 6 | 비교나 증감을 묻는 질문이면, 순위와 증감률을 **코드가 다시 계산**합니다. 답변의 결론과 다르면 한 번 고쳐 쓰게 합니다 | `agent/compare.py` |
| 7 | 근거를 찾지 못하면 에이전트 경로로 넘어가 다시 조사합니다 | `agent/loop.py`, `agent/tools.py` |

에이전트가 쓰는 도구는 네 가지입니다. 회사 이름 확인, 공시 목록 조회, 공시 검색, 섹션 원문 읽기입니다.

## 3. 보고서가 만들어지는 과정

| 순서 | 하는 일 |
|---|---|
| 1 | 저장본이 있고 버전이 같으면 바로 보여 줍니다 |
| 2 | 섹션마다(사업 구조, 실적, 판매, 생산, 리스크, 주주) 위키에서 해당 페이지를 읽습니다 |
| 3 | Luna가 섹션을 씁니다. 순서는 **특징 → 데이터 표 → 해석**입니다. 여러 섹션을 동시에 씁니다 |
| 4 | 마지막으로 "한눈에 보기"를 씁니다. 다른 섹션의 결과만 읽고 요약합니다 |
| 5 | 인용된 숫자와 표의 숫자를 원문과 대조합니다 |
| 6 | 오류가 없으면 저장합니다 |

- 섹션 구성은 `config/report_templates.yaml`에서 바꿉니다.
- 코드는 `report/builder.py`에 있습니다.
- 프롬프트나 섹션 구성을 바꾸면 버전이 바뀌어, 저장본 대신 새로 만듭니다. 이때 바뀐 섹션이 들어가는 공시 유형만 다시 만듭니다.

## 4. 핵심 설계와 근거

| 설계 | 이유 | 측정 결과 |
|---|---|---|
| 공시의 목차와 표 구조를 살려서 가공 | 위키, 검색, 보고서가 모두 이 구조를 씁니다 | |
| 위키 경로 | 답이 한 섹션에 있으면 검색할 필요가 없습니다 | 근거 수집 시간이 거의 0 |
| 의미 검색 + 단어 검색(BM25) | 공시 질문은 계정 이름과 숫자처럼 정확한 단어가 중요합니다 | 검색 성공률 58% → 78% |
| 규칙 라우터를 먼저 쓰기 | 규칙으로 확실한 질문은 LLM을 부를 필요가 없습니다 | 응답 시간 중앙값 5.7초 → 4.4초 |
| 숫자 판단은 코드가 검증 | LLM은 원문은 정확히 옮기지만 대소 비교나 계산에서 실수합니다 | 결론 정확도 91% → 95% |
| 보고서는 미리 생성 | 생성에 약 14초가 걸리지만, 저장본은 바로 열립니다 | 공시 1건당 약 6원 |

## 5. 폴더 안내

| 폴더·파일 | 내용 |
|---|---|
| `dart_rag/ingestion/` | 공시 다운로드, 구조 분석, 청크 나누기 |
| `dart_rag/pipeline/` | 데이터 준비 단계를 순서대로 실행하고 진행 상황을 기록 |
| `dart_rag/embedding/`, `dart_rag/index/` | 임베딩, 검색 인덱스, 청크 저장소 |
| `dart_rag/retrieval/` | 질문 분석과 하이브리드 검색 |
| `dart_rag/routing/` | 라우터와 auto 모드 답변 |
| `dart_rag/agent/` | 에이전트, 프롬프트, LLM 호출, 비교 검증 |
| `dart_rag/report/` | 보고서 생성과 저장 |
| `dart_rag/wiki.py` | 위키 만들기와 읽기 |
| `dart_rag/service.py` | 위 부품들을 하나로 조립 |
| `dart_rag/api.py`, `cli.py` | 웹 서버, 터미널 명령 |
| `web/index.html` | 테스트용 화면 (질문 탭, 보고서 탭) |
| `config/` | 설정 파일 (아래 6절) |
| `eval/`, `scripts/eval_qa.py` | 성능 평가 문항, 평가 결과, 평가 스크립트 |
| `tests/` | 자동 테스트 (실제 API를 부르지 않아 비용이 들지 않습니다) |

`generation/`과 `llm/`은 auto와 에이전트가 모두 실패했을 때 쓰는 예비 경로입니다.

## 6. 설정 파일로 바꿀 수 있는 것

코드를 고치지 않아도 됩니다.

| 하고 싶은 일 | 파일 |
|---|---|
| 질문 주제와 위키 섹션 연결 추가 (예: "배당" → 배당 섹션) | `config/wiki_routes.yaml` |
| 회사 별칭 추가 (예: 현차 → 현대자동차) | `config/agent.yaml`의 `aliases` |
| 동의어 추가 (예: 빚 → 부채총계) | `config/lexicon.yaml` |
| 보고서 섹션 추가, 지시문 수정 | `config/report_templates.yaml` |
| 라우터 종류, 답변 길이 상한, 에이전트 라운드 수 | `config/agent.yaml` |
| 임베딩 모델, 저장 방식 | `config/settings.yaml` 또는 `.env` |

## 7. 성능 평가

평가 문항 56개(`eval/qa_eval.yaml`)로 측정했습니다. 문항은 사실, 동의어, 개념, 비교, 추이, 계산, 상대 기간, 원인, 답이 없는 질문으로 나뉩니다. 정답 숫자는 모두 공시 원문에서 확인한 값입니다. 실행 방법은 README의 "4-2. 성능 평가"를 보세요.

| 항목 (auto 모드) | 개선 전 | 개선 후 |
|---|---:|---:|
| 답변 정확도 | 95% | 98% |
| 비교·추이·계산 결론 정확도 | 91% | 95% |
| 원문과 맞지 않는 근거 비율 | 2% | 0% |
| 에이전트로 넘어간 비율 | 21% | 11% |
| 응답 시간 (중앙값) | 5.7초 | 4.4초 |
| 응답 시간 (느린 쪽 10%) | 14.4초 | 10.0초 |
| 질문 1개당 비용 | 약 1원 | 약 1원 |

답이 없는 질문(보유하지 않은 회사나 기간)에 숫자를 지어낸 경우는 개선 전후 모두 0건이었습니다.

## 8. 남은 과제

| 과제 | 내용 |
|---|---|
| 에이전트 속도 | 에이전트 경로는 15~22초가 걸립니다. 회사와 공시 목록을 미리 알려 주면 조사 단계를 1~2번 줄일 수 있습니다 |
| 표 단위 누락 | 일부 표는 구조 분석 과정에서 단위가 빠집니다 (예: 삼성전자 연구개발비) |
| Gemini 사용 한도 | 무료 등급은 분당 15회입니다. 사용자가 많으면 규칙 라우터로만 동작합니다 |
| 계획서와 다른 점 | DB는 계획서의 PostgreSQL 대신 SQLite를 씁니다(PostgreSQL 코드는 있음). LangChain은 쓰지 않고 직접 구현했습니다. 대화 이력과 재무 수치 구조화는 아직 없습니다 |
| 평가 문항 | 구조를 아는 사람이 만든 56문항이라 실제 질문보다 쉬울 수 있습니다. 팀원과 테스터의 질문을 추가하면 좋습니다 |
